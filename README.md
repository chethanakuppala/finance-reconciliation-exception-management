# Financial Reconciliation & Exception Management

An end-to-end reconciliation pipeline over a simulated finance back office —
AP sub-ledger, disbursements, general ledger and bank statements for three
entities across nine periods of FY2026. Thirteen controls raise fourteen
exception types, an AI-assisted layer triages each exception behind a ten-check
validation gate, and the whole thing ties out: the GL-to-sub-ledger variance is
decomposed to a **USD 0.01** unexplained residual across three entities.

> **Synthetic data.** The 62 vendors, 1,816 invoices, 1,600 payments, 8,779
> journal lines and 1,597 bank lines are generated by `generate_data.py`. The
> defects the controls find were deliberately injected and logged to
> `data/seeded_defects.csv` — which is what makes the detection recall and
> precision figures in this repository measurable rather than asserted. No
> figure comes from any real company's records. What is demonstrated here is
> the **control design, the matching logic and the assurance method**, not an
> empirical finding.

| Cash at risk | USD 1.60M · USD 433k recovered |

| `sql/schema.sql` | Warehouse DDL — 10 tables, indexes and 5 reconciliation views |
| `sql/reconciliation_queries.sql` | The same controls written independently in SQL, plus 5 reporting queries |

| `build_dashboard.py` | Builds `dashboard.html` from the JSON output |
| `dashboard.html` | Self-contained interactive dashboard — open it in a browser |
| `docs/DATA_DICTIONARY.md` | Every field, its meaning, and the source-to-target mapping into the BI model |
| `docs/RECONCILIATION_RULES.md` | The control catalogue: objective, rule, tolerance, owner, remediation |
| `docs/TEST_SCENARIOS.md` | Seeded defect scenarios, detection results, threshold tests, known limits |

## Three things this repository is really about

**1. A control you cannot measure is a claim.** The generator injects defects
and logs them; the engine never reads that log. Afterwards, recall and precision
are computed per control. One strict-recall miss survives at 99.2%, and
[docs/TEST_SCENARIOS.md](docs/TEST_SCENARIOS.md) explains exactly why it is a
data limitation rather than a tuning problem — along with why three "false
positives" on the duplicate-payment control turned out to be the control being
right.

**2. A variance you cannot decompose is not reconciled.** The AP control account
does not agree to the sub-ledger by USD 314.9k. Stopping there is where most
monthly reconciliations stop. The tie-out splits that number into missing
postings, FX posting errors, topside entries and FX on settlement, derived from
the ledger itself, and reports the residual. At USD 0.01 it says the exception
register accounts for the whole difference — a materially stronger statement
than "within threshold".

**3. An AI layer in finance needs a gate, not trust.** The triage layer assembles
an evidence pack, proposes a root cause and an action from a closed list, and
submits it to ten checks — including numeric grounding (every figure must trace
to the evidence), identifier grounding, an action policy matrix, a sensitive
data screen and a cross-check against a deterministic baseline. A blocking
failure falls back to the baseline and forces human review. It never closes an
exception; nothing in that layer writes to the exception status.

## Design notes

- **Two implementations on purpose.** Every control exists in pandas and in SQL.
  `build_warehouse.py` fails the build when they disagree, which turns the
  control specification into something testable rather than something asserted.
- **Deterministic end to end.** Fixed seeds throughout, including the simulated
  workflow state, so every figure in the documentation is reproducible from a
  clean clone.
- **No API key needed.** The AI layer's default provider is a deterministic
  analyser that writes the same schema the model does — which is also the
  baseline every model response is cross-checked against.
- **Charts built to be read.** The dashboard palette is validated for
  colour-vision deficiency in both light and dark modes; severity uses an
  ordered single-hue ramp rather than status colours; every chart carries a
  table view, and no chart uses a second y-axis.
